# AltMount preparation and delivery contract

Research date: 2026-11-07. Planning evidence only; no service execution, deployed-host inspection, benchmarking or product changes.

## Identity and version boundary

The intended Usenet project is **kipsilabs/altmount**, formerly referenced as javi11/altmount. The current README names the kipsilabs module/container and links the official documentation. Its latest published release is **v0.4.0**, published 2026-11-04, tag commit **276157560ecd510de127c69b5368aaa0e0ce4277**. Current main observed at **0a8b9a8417c1d03ca103c193075dd04ea7ff2680** differs by one commit affecting only Stremio addon metadata and its test; the preparation, file-stream, queue, WebDAV and auth source discussed below is therefore also release source. These are upstream versions, not evidence of the owner's installed version. ## Authentication and mount versus endpoint

Most management REST endpoints use JWT when login is required. The official login flow sets an HTTP-only JWT cookie; docs also describe Bearer and X-JWT. A general ?apikey parameter is not a substitute. /api/nzb/streams authenticates internally through raw **X-Api-Key** or **download_key** (SHA-256 of the user's API key, form/query). Its generated media URLs require the hashed **download_key query parameter**; the actual stream handler requires this even though a stale comment says authentication can be skipped. The hash is a usable bearer credential, not a public non-secret identifier or expiring per-file grant. WebDAV separately accepts configured Basic credentials or JWT; anonymous WebDAV depends on login configuration, while explicit invalid Basic credentials fail. [API docs](https://github.com/kipsilabs/altmount/blob/276157560ecd510de127c69b5368aaa0e0ce4277/docs/docs/4.%20API/endpoints.md), [submission auth](https://github.com/kipsilabs/altmount/blob/276157560ecd510de127c69b5368aaa0e0ce4277/internal/api/nzb_stremio_handlers.go), [stream auth implementation](https://github.com/kipsilabs/altmount/blob/276157560ecd510de127c69b5368aaa0e0ce4277/internal/api/stream_handler.go), [WebDAV auth](https://github.com/kipsilabs/altmount/blob/276157560ecd510de127c69b5368aaa0e0ce4277/internal/webdav/adapter.go).

A FUSE/rclone mount produces a filesystem path on a host. It does not make that path reachable by a TV/player. AltMount also serves HTTP directly: /api/files/stream or authenticated WebDAV GET. Those URLs must be player-reachable, or KF must relay bytes. The route constructs URLs from configured Stremio base URL/request context, so reverse-proxy/public URL correctness remains a deployment contract. No host, topology or direct-versus-relay decision is made here. [URL construction](https://github.com/kipsilabs/altmount/blob/276157560ecd510de127c69b5368aaa0e0ce4277/internal/api/nzb_stremio_handlers.go), [native HTTP routing and optional mount start](https://github.com/kipsilabs/altmount/blob/276157560ecd510de127c69b5368aaa0e0ce4277/cmd/altmount/cmd/setup.go).

## Comparison with KF's NzbDAV responsibility map

The existing map covers submission, polling/cancellation, WebDAV library traversal/video selection, byte probing, shared preparation caches, delivery modes/ranges, cleanup, auth and KF fallback. It pins historical c83a3c7 behavior and flags test/deployment limitations, so it is a responsibility baseline, not proof that every historical defect still exists. [KF map at the requested checkpoint](https://github.com/ReyesPascal/KaijuFlow/blob/6565c1a7c810e2cb2bf7d4e1239e545adbd4236e/docs/kaijuflow/references/nzbdav/ARCHITECTURE.md).

AltMount can fit the **selected NZB → preparation handle/state → selected virtual file and media access** portion of that boundary. Two observed integration surfaces are synchronous stream resolution and SAB/queue preparation with separate lookup. Neither requires delegating KF discovery/indexers/ranking/source fallback to AltMount. AltMount's own addon search/scoring and health/ARR automation are additional features, not required owners of KF responsibilities. KF health eligibility and backend file-read/repair status must remain distinct. This is a fit inference from the pinned APIs, not an accepted adapter design. [AltMount routes](https://github.com/kipsilabs/altmount/blob/276157560ecd510de127c69b5368aaa0e0ce4277/internal/api/server.go), [KF baseline](https://github.com/ReyesPascal/KaijuFlow/blob/6565c1a7c810e2cb2bf7d4e1239e545adbd4236e/docs/kaijuflow/references/nzbdav/ARCHITECTURE.md).

The owner still needs to choose the preparation surface, KF readiness/probe policy, selection responsibility, reachable delivery/auth strategy, cancellation ownership for shared work, and retention/deletion policy. NzbDAV's /content/category/title and /.ids/job lookup rules, cached XML flow, automatic retries and proxy buffering are not portable contracts merely because both services advertise SAB/WebDAV. Verify deployed versions and actual request/seek/cancellation behavior later using the existing benchmark plan; no comparative speed or replacement recommendation follows from this research.
