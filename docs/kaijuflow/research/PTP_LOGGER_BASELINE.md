# PTP-Logger baseline for Jetstream

Research date: 2026-11-07. Source inspection only; no software execution, builds, host/device access, live log collection or product changes. Destination: Android TV Jetstream retaining useful PTP playback/Dolby Vision behavior, with KaijuFlow first and Fusion as a design reference. Existing host-specific collectors are inventory, not a proposed Jetstream deployment.

## Schema, identifiers and clocks

PTP [formatter/rolling files](https://github.com/ReyesPascal/Pascal-The-Popcorn/blob/fbf14f6e77f3cfc7a26b1004662d868a5a517a85/app/src/main/kotlin/com/arflix/tv/util/diag/DiagFormat.kt) uses `{e,t,seq,id,lvl,...scalarFields}`: event name, wall-clock epoch milliseconds, process-local sequence, an eight-hex identifier derived from a short process UUID hash XOR sequence, and uppercase D/I/W/E. It bounds fields/line size, can truncate, masks UUID path segments, and keeps at most five 10 MiB files. This is a local event identifier, not a stable playback session or globally unique distributed trace contract. Monotonic clocks measure many local durations; cross-device wall clocks are not synchronized by this code.

Logger [eventLog](https://github.com/ReyesPascal/PTP-Logger/blob/935b2917c349757a46eb6c22703d46662de8434d/server/eventLog.ts) stores `{id,ts,seq,level,eventType,message,source,device?,payload?}`, assigning a fresh 12-hex random ID and process-local sequence, normalizing time to UTC. PTP parsing preserves original fields in payload, names events ptp-<e>, uses app time, and deduplicates up to 50,000 PTP IDs in memory. That PTP parser dedupe set keys only id, not device, and is not persisted; collisions or restart duplicates remain possible.

**Source mismatch requiring later review:** the PTP formatter emits uppercase severity, while logger ptpDiag's level map uses lowercase d/i/w/e and falls back to info. As written, ordinary uppercase W/E PTP records become info in the unified store. Its lowercase d also maps to info. This conclusion follows directly from the two pinned files; no live failure was observed.

Media3 loadTaskId is useful within player loads; IMDb/TMDB/episode IDs connect content context; source indices/names connect local choices. None identifies a specific KF request across discovery, preparation, redirects, source switching and playback. The audio session ID visible in PlayerScreen is for Android audio effects, not a distributed playback session.

## Transport, persistence and export

The current PTP writer has no HTTP sender: logcat plus rolling files are the implemented path. Logger's [ingest receiver](https://github.com/ReyesPascal/PTP-Logger/blob/935b2917c349757a46eb6c22703d46662de8434d/server/ingest.ts) accepts POST /api/ingest: device plus up to 1,000 events with client id, ISO ts, level, eventType, message and optional payload; [server](https://github.com/ReyesPascal/PTP-Logger/blob/935b2917c349757a46eb6c22703d46662de8434d/server.ts) caps body at 2 MiB. It validates the whole batch, writes source ptp-app with client timestamp, returns accepted/duplicates, and remembers latest 50,000 hashed (device,id) pairs, saving after event flush every 10 seconds/shutdown. Client id is a dedupe key and is not retained as stored id. Eviction/crash windows mean at-least-once, not exactly-once. The README's durable offline TV queue/retry/acknowledgement policy is explicitly a **1.0.3 sender requirement**, not an implementation demonstrated in this PTP snapshot.

Logger appends daily UTC JSONL with 50 MiB parts before ring/SSE publication, syncs every second and on flush, and skips torn prior lines while reading. The memory ring is 5,000 events. [Server APIs](https://github.com/ReyesPascal/PTP-Logger/blob/935b2917c349757a46eb6c22703d46662de8434d/server.ts) provide filtered queries/cursors, timeline windows, IMDb text-match title summaries, JSONL/CSV export and SSE with 20-second heartbeat/backpressure disconnect. Title matching is not a structured session join; SSE is observation delivery, not playback feedback.

[Retention](https://github.com/ReyesPascal/PTP-Logger/blob/935b2917c349757a46eb6c22703d46662de8434d/server/retention.ts) compresses closed days and deletes expired days only after verified archive state; default setting is 14 days. [Archive](https://github.com/ReyesPascal/PTP-Logger/blob/935b2917c349757a46eb6c22703d46662de8434d/server/archive.ts) uses rclone copy/check with download verification, records verified file state, and retries failures. These implemented workers supersede stale README claims; successful remote archiving is unverified. Logger stores payloads without general redaction and exposes no authentication middleware in these routes. PTP's specialized masking and [AppLogger](https://github.com/ReyesPascal/Pascal-The-Popcorn/blob/fbf14f6e77f3cfc7a26b1004662d868a5a517a85/app/src/main/kotlin/com/arflix/tv/util/AppLogger.kt) sanitization do not establish end-to-end privacy guarantees for raw logcat/container/host inputs.

## Reuse boundary and missing proposal pieces

Retain as candidates: PTP's bounded diagnostic facade/formatter, player and HTTP observation hooks, source-selection diagnostics, logger query/export timeline and optional ingestion receiver. Their useful behavior can support a Jetstream player/DV investigation. Adapt PERSONAL_BUILD gating, package path, service/container labels, device discovery and storage/privacy policy deliberately; no Brain-heavy topology is required.

The pinned code establishes neither shared KF/PTP request/session propagation nor a playback-outcome endpoint feeding KF ranking. A future design could carry explicit correlation in payloads, but must define lifecycle and distinguish release, preparation attempt, integration instance, playback attempt and device incompatibility from dead NZBs. Preserve any event client ID needed for joins rather than relying on ingest's discarded dedupe ID. No implementation or owner acceptance is implied.

Likewise, log messages/probes do not supply an explicit backend preparation state machine, progress percentage/ETA, warm-up API or device-aware ranking contract. These remain separate proposals to evaluate against KF ownership and the already researched playback boundary. This report recommends no KaijuNNTP extraction, automatic integration fallback, alternative backend promotion or codec fallback.
