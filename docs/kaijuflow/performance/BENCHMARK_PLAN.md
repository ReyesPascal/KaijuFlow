# Separate NNTP / NzbDAV performance milestone

Tracking: [Issue #4](https://github.com/ReyesPascal/KaijuFlow/issues/4). Status: **proposed plan; no measurements executed**. This is separate from closed A4. Issue #2 remains the open handoff tracker. Planning and documentation are authorized; benchmark execution needs a separately scoped, non-production environment and legal corpus. No Brain access, production configuration changes, deployment, application fixes or engine implementation are authorized here. Keep both repositories private.

Preserve NzbDAV as the known-good solution until a measured candidate proves superior under the gates below. Existing synthetic validation establishes only bounded behavior; it provides no throughput, real 4K or first-frame baseline. In particular, [INT-DISCOVERY-STREAM-001](../audit/INTEGRATION-DISCOVERY-STREAM.md), evidence `EV-KF-INT-001`, transferred 64 non-decodable bytes using a fake immediately completed NzbDAV job and a supplied health verdict. It is not a benchmark.

## Repeatable protocol

1. Freeze Git SHAs, dependency locks, Node and NzbDAV versions, OS/kernel, CPU/core count, RAM, disk model/filesystem, network interfaces/route/link rate, staging topology and clock sources. Record player/device/version, decoder settings and display mode. Keep identical hardware and player across arms; prohibit competing workloads. Never transplant production credentials into evidence.
2. Use a legal owned/generated corpus with stable object hashes, codec/container, duration, resolution, average bitrate and a 1-second bitrate trace. Include a representative original 4K source with high-bitrate peaks, one direct video NZB and a clearly labeled archive class. Restrict conclusions to the tested corpus. NNTP provider/source, retention and account connection limits must be recorded privately and held constant for paired comparisons.
3. Freeze Smart/Fixed mode, sampling, provider ordering, source list, proxy path, stream mode, buffer capacities and timeouts. Freeze source-choice semantics: a faster lower-quality source is not an equivalent win. Record the actual selected content hash on every successful trial. Keep data integrity and security constraints constant.
4. Define cache state explicitly. **Cold**: new disposable application/NzbDAV data and cache state for each trial, with OS page-cache policy documented on staging. **Warm metadata**: retain application result/health/path caches but identify whether media is already present. **Warm media**: retain exactly the completed media object and document page-cache state. Do not merge these populations or call metadata warm a full-media cache hit. Reset only staging resources.
5. Use a fixed schedule of forward/backward/near-end seeks and identical concurrency levels (1, 2, 4). Start with ten paired cold starts and ten paired warm starts per source/arm; obtain at least ten seek observations per seek class. Alternate/randomize A/candidate order using a recorded seed to limit changing provider/network conditions. Each sustained trial runs at least 30 minutes, or full duration for shorter sources with that limitation stated.
6. Capture monotonic timestamps for play action, discovery completion, health completion, NZB grab/submission, job completion, WebDAV ready probe, first HTTP byte, **player first presented frame**, each seek action/resumed frame, and every rebuffer start/end. Correlate trace IDs across services without exposing API keys or URLs with secrets. HTTP first byte is a separate metric and cannot substitute for first frame.
7. Sample active/idle NNTP connections and resource counters every second: per-process CPU, RSS and peak RSS, disk bytes/IOPS/latency, network bytes/errors/retransmissions, and buffer occupancy where instrumentation exists. Record host totals too. Collect provider errors, retries, reconnects, selected fallback and delivered byte ranges/hashes. Mark unavailable counters as missing; do not estimate them as measured.
8. Report individual trial records, p50/p95, min/max, failure counts, paired deltas and uncertainty. Ten trials are a screening minimum; p95 is coarse at this size. An apparent improvement near noise is inconclusive, and a larger separately approved sample is needed before promotion. Preserve all failed runs and classify environment versus application failures without silently excluding either.

## Proposed measurable acceptance gates

All numeric thresholds below are **proposed**, not measured product guarantees. Freeze them in Issue #4 before running trials. Evaluate each cache state, source and concurrency level separately. A candidate must satisfy correctness/reliability gates, show a repeatable benefit in at least one target metric, and avoid material regression elsewhere.

| Metric | Definition / instrumentation | Proposed acceptance criterion |
| --- | --- | --- |
| Startup latency | Play action to first delivered HTTP media byte; also report discovery/health/preparation component times | Candidate p95 no worse than baseline by more than max(10%, 250 ms); a startup-focused candidate must improve paired median at least 20% with uncertainty excluding zero |
| Time to first frame | Play action to player-confirmed first presented frame, not first byte | Candidate p95 no worse than baseline by more than max(10%, 500 ms); TTFF-focused improvement at least 20% paired median; no decode failures |
| Sustained throughput | Delivered original media bits/s over 1 s and 30 s windows, with source bitrate trace aligned to playback | Mean available delivery capacity at least 1.5× original mean 4K bitrate; at least 99% of 30 s windows meet 1.2× corresponding source bitrate demand during uncapped retrieval trials; playback itself must avoid buffer starvation. Report peak-bitrate headroom separately |
| Seek latency | User seek to first presented frame at the requested timestamp, per seek direction/distance | p95 at most 3 s on warm media and 8 s cold, and no worse than baseline by more than max(10%, 250 ms); requested frame/byte mapping correct |
| Rebuffering | Count and duration of stalls after initial playback, excluding explicit seek intervals which are reported separately | Zero unplanned rebuffer events during a stable 30-minute single-player trial; multi-player total stalled time under 0.1% and no stall over 2 s; never worse than baseline |
| Cache cold/warm | Same startup, TTFF, seek and throughput metrics stratified by the three cache definitions above | All correctness gates pass in every state; no state-specific p95 regression above its metric allowance; report warm/cold ratios and bytes fetched to show where benefit originates |
| NNTP connections | Active/idle/peak socket counts per provider and process, including retries | Never exceed configured provider/account cap; no monotonically growing idle count after trials; return to documented idle baseline within 60 s. A connection-saving candidate must reduce peak or connection-seconds at least 20% without throughput regression |
| CPU / RAM | Process CPU-seconds per delivered GiB, steady/peak RSS, host headroom | No OOM/crash; peak RSS under 80% of assigned staging RAM and p95 CPU under 80% of assigned core capacity at target concurrency. Candidate resource increase above 10% needs an explicitly accepted latency/throughput tradeoff; resource-focused candidates improve target at least 20% |
| Disk / network | Disk read/write bytes per delivered GiB, latency/IOPS, network bytes per delivered GiB, retransmits | No disk-full or unbounded growth; document cache footprint and cleanup; baseline-normalized disk/network amplification no more than 10% worse absent explicit tradeoff; maintain throughput and seek gates |
| Provider/source fallback | Controlled staging failure/throttle/restore; detection-to-recovered-delivery and player stall | Ten repetitions per defined fault; 10/10 return correct bytes/source quality with no silent corruption; p95 recovered delivery within 10 s for recoverable faults, no retry loop exceeding the frozen retry budget; report fault-induced buffering separately |
| Integrity / equivalence | Object/range hashes, codec/container identity and expected frame timeline | 100% checked bytes/ranges match the selected original object; no transcoding or silent quality reduction; unsupported archives explicitly rejected/labeled, not counted as successful playback |

For throughput, a player that reads at playback speed may conceal spare capacity. Use a separately labeled staging capacity trial with the same retrieval path and an uncapped sink, then correlate with player trials. Never infer 1.5× headroom merely from zero buffering or metadata bitrate.

## Faults, evidence and decision

Use only separately authorized staging fault controls; never alter production networking. Define the exact endpoint, loss/throttle profile, outage duration, expected fallback source and restoration timestamp before each fault group. Include a source failure and a provider connection failure, preserving identical data-quality requirements. Stop a group on integrity loss, resource exhaustion or evidence that the staging boundary is wrong; retain the failed trace.

Save a sanitized manifest with trial ID, arm, SHAs, fixture hash, environment fingerprint, cache state, seed, timings, counters, outcome, exclusions and known gaps. Store raw traces privately with SHA-256 and a stated retention policy; commit small scrubbed summaries and reproducible configuration templates only. Do not expose provider credentials, identifiable private NZBs or production details. Future measurement evidence must use `measured` classification with run IDs; this plan remains `proposed`.

Promote an alternative only after equivalent content, correctness, recovery and resource gates pass and paired results show a useful benefit beyond uncertainty. An inconclusive comparison retains NzbDAV. Benchmark success authorizes neither merging nor deployment; those remain separate decisions. The next authorized action is reviewing/finalizing this plan and selecting an explicitly approved non-production environment, not executing production benchmarks.
