## Gate verdict — A4-ISO-000 PASS

Verified on [private GitHub Actions A4 run 42366142956](https://github.com/ReyesPascal/KaijuFlow/actions/runs/42366142956), a GitHub-hosted Ubuntu 24.04 / Node 20 workflow. The runner compiled unchanged imported backend source (test setup only). A separate, disposable Linux network namespace was created with the loopback interface alone. **Before importing any application module**, an unprivileged Node probe checked:
- outward IPv4 TCP to `192.0.2.1:443` and IPv6 TCP to `2001:db8::1:443` both produced routing-denial errors;
- outbound UDP DNS transport to `1.1.1.1:53` was denied; a fabricated `.invalid` hostname failed to resolve;
- a synthetic local HTTP server was reachable over `127.0.0.1`;
- a negative-control probe with `A4_FORCE_FAIL=1` returned exact exit 77 **after** successful network probes and halted before the application-import sentinel appeared; a distinct positive probe printed `A4_ISOLATION_GATE_PASS`.
- all application execution happened after the positive gate under unprivileged `nobody`, using copied compiled files, local node_modules and original public placeholder MP4 assets under `/tmp`; all local HTTP mocks bound to loopback.
- pinned `src/` and `ui/src/` Git diff was empty before and after, and per-file SHA-256 source manifests were identical.

The isolation guard was validated as a **separate gate**. The combined A4 workflow intentionally exits nonzero when a later behavioral assertion fails; a red overall CI result does not negate the logged and reproduced isolation-gate PASS. This is not a claim of a fully hardened OS filesystem sandbox or of a complete live-app boot. The disposable runtime uses bounded original-module imports/Express router mounts instead of `src/server.ts` startup.
