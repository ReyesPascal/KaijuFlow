KaijuFlow REA Execution and Indexed Evidence Strategy
Executive summary
The proposed Stages 0–5 plan is fundamentally sound, but it should be refined in three ways.

First, REA should be treated as an artifact-level, evidence-producing analysis layer rather than the primary source-code architecture tool. REA 6.8.0 can statically inspect JavaScript application directories without executing them and without Ghidra, returning an application graph, artifact identities, source locations, coverage, limitations, and Evidence records. Its JavaScript analyzer also supports explicit source selection, but selected files do not automatically pull in their imports, so targeted analyses must deliberately include supporting manifests, source maps, and related modules. 

Second, the isolated Node 24.22.2 runtime is the correct REA runtime. REA 6.8.0 declares support for Node ^22.23.4 || ^24.22.1 || >=26.12.1; therefore production Node 22.22.1 is below REA's supported floor, while isolated Node 24.22.2 satisfies it. Node 24 is currently an LTS line; Node 20 reached end-of-life in March 2026, so the already-passed Node 20 build remains useful as compatibility evidence but should not become the REA execution environment. 

Third, the evidence store should be versioned beside the imported source but divided into small, reviewable metadata/index files and potentially large raw evidence artifacts. REA warns that full application Evidence can reach hundreds of megabytes; its CLI supports projecting summaries and module pages from saved Evidence rather than repeatedly loading or committing giant reports. GitHub's own REA CI example similarly saves stdout, stderr, and exit status separately and explicitly warns that a zero exit code does not imply full coverage.

The most important change from the earlier plan is methodological: do not ask REA to prove runtime behavior. Use it to identify and preserve artifact-level relationships, source locations, boundaries, integrity, coverage and unknowns; use ts-morph/dependency-cruiser for source architecture; Vitest for deterministic service behavior; Playwright for browser/UI behavior; and CodeQL where security-oriented interprocedural data-flow analysis adds value. dependency-cruiser is specifically designed to validate and visualize JS/TS dependency relationships; CodeQL provides JavaScript/TypeScript data-flow and taint analysis; Vitest provides mocks and coverage; and Playwright supplies isolated browser contexts and cross-browser execution. 

No part of this plan requires modifying Brain production containers or merging a PR. The preferred execution target is the ThinkPad's isolated Node 24 environment and a disposable checkout/worktree.

REA's JavaScript analyzer is deliberately parse-not-execute for static application analysis, and its Evidence retains artifact digests, manifests, coverage and explicit limitations. REA also states that source selection changes analysis scope while the complete artifact remains inventoried; imports do not automatically expand selected sources. Those properties are exactly why it is useful as an independent artifact witness but insufficient by itself to establish live NNTP or streaming behavior. 

Ghidra 12.1.4 should therefore remain available but dormant during the initial KaijuFlow work. REA says static JavaScript analysis needs no native engine; Ghidra is appropriate if the audit later discovers native .node add-ons, bundled ELF/PE binaries, proprietary helpers, or another native component whose behavior is material. Ghidra itself is a compiled-code SRE framework offering disassembly and decompilation rather than a TypeScript application architecture analyzer.

The interpretation questions should be narrowly phrased:

Which built modules implement candidate selection and checking?
What observable artifact relationships support a Smart-versus-Fixed distinction?
Where are stop conditions represented in the built artifact?
Which provider-checking dependencies cross the selected-source boundary?
Does REA expose a source location/source-map link that can be reconciled to the canonical TypeScript source?
A claim such as “Smart stops after N healthy candidates under condition X” is not accepted merely because an artifact graph suggests that path. It becomes a behavioral claim only after Stage 3 reproduces it with deterministic tests.

Subsystem prioritization and tool allocation
The key principle is to use the tool whose data model matches the question. ts-morph exposes TypeScript AST/project information; dependency-cruiser analyzes module dependencies and rules; CodeQL is built for interprocedural data-flow/taint questions; REA reconstructs and preserves artifact evidence; Vitest isolates deterministic service behavior; Playwright exercises browser-visible behavior. 

Subsystem	Why it matters	Recommended tool(s)	Exit gate
Smart/Fixed candidate selection	Central policy logic and high risk of subtle early-termination differences.	ts-morph → REA targeted artifact corroboration → Vitest.	Exact source decision path mapped; built artifact correspondence established; deterministic tests prove top-N/stop behavior and error paths.
Health/article availability checking	Async fan-out, provider failover, timeouts and cancellation are hard to establish statically.	ts-morph, REA for built call relationships, Vitest fake NNTP services.	Primary/pool/backup behavior, cancellation and connection cleanup reproduced under synthetic failure scenarios.
NNTP transport	Protocol/state/network behavior dominates correctness.	Source analysis + Vitest/local fake NNTP; CodeQL for credential/logging flow. REA only as corroboration.	No live credential dependency; connect/auth/article/error/timeout flows tested; sensitive flows mapped.
NzbDAV submission/client	External-system boundary and likely source of configuration/data exposure.	ts-morph, REA targeted artifact analysis, Vitest fake HTTP/WebDAV endpoint.	Request formation, error handling, retries and persistence demonstrated without live NzbDAV.
HTTP streaming/ranges	Observable protocol semantics matter more than source shape.	Source analysis, Vitest integration server, Playwright where browser behavior matters.	Correct 200/206/416, ranges, seeking, disconnect and fallback under isolated fixtures.
Fallback orchestration	Cross-subsystem control flow can diverge between source intent and build output.	dependency-cruiser + ts-morph + REA + Vitest.	All fallback edges identified; precedence and terminal conditions reproducibly tested.
Indexer/Newznab aggregation	External input normalization, ranking and failure handling.	ts-morph, dependency-cruiser, Vitest fixture responses; CodeQL for URL/credential flows.	Normalization/ranking/dedupe/failure cases covered with fixture corpus.
Caching/persistence	State lifetime changes behavior and may leak sensitive data.	ts-morph, CodeQL, Vitest with temporary filesystem/storage.	Cache key/content/TTL/invalidation mapped and tests prove isolation plus cleanup.
React/UI	Static REA adds relatively little when original TypeScript/JSX is available.	ts-morph + Playwright; dependency-cruiser for frontend boundaries.	User flows and API calls validated in isolated browser tests.
Configuration/auth/secrets/logging	Highest confidentiality concern.	CodeQL + source review + tests; REA only if compiled output differs materially.	Secret sources/sinks/log paths inventoried; no fixture or evidence artifact contains real secrets.

dependency-cruiser can report circular dependencies, unresolved imports and rule violations and can emit JSON or graph formats, which makes it particularly useful for A3's whole-app topology. 

CodeQL should be reserved for questions such as “can a credential/config source reach a logging sink?” or “can untrusted indexer data reach a dangerous operation without sanitization?” because its JavaScript/TypeScript libraries model local and interprocedural data flow and taint tracking. Repository availability depends on GitHub plan/repository visibility if GitHub-hosted code scanning is used; private/internal repositories require GitHub Code Security, although local CodeQL workflows are a separate deployment question. 

CI isolation, privacy, and security controls
GitHub Actions design
REA's official CI documentation recommends a pinned, noninteractive CLI workflow using GitHub-hosted Ubuntu, states that static JavaScript analysis needs no Ghidra/Java/browser/Docker/API key, and recommends keeping the tool installation separate from application dependencies. Its example requests only contents: read and warns against executing untrusted PR code in privileged contexts. 

For KaijuFlow, prefer workflow_dispatch initially and then optionally a normal pull_request job after the workflow has been reviewed. Do not use pull_request_target to check out and execute PR code; GitHub explicitly warns that this combination can expose privileged credentials and repository resources. 

A minimal workflow shape is:

yaml
Copy
name: REA isolated JavaScript audit

on:
  workflow_dispatch:
  # Enable only after review:
  # pull_request:
  #   paths:
  #     - 'src/**'
  #     - 'package*.json'
  #     - '.github/workflows/rea-audit.yml'

permissions:
  contents: read

jobs:
  rea-static:
    runs-on: ubuntu-24.04

    env:
      REA_VERSION: '6.8.0'
      REPORT_DIR: ${{ runner.temp }}/rea-report

    steps:
      - name: Prepare report directory        shell: bash
        run: mkdir -p "$REPORT_DIR"

      - name: Checkout
        uses: actions/checkout@v6

      - name: Use Node 24
        uses: actions/setup-node@v7
        with:
          node-version: '24.22.2'
          cache: npm

      - name: Record environment
        shell: bash
        run: |
          node --version | tee "$REPORT_DIR/node-version.txt"
          git rev-parse HEAD | tee "$REPORT_DIR/source-commit.txt"
          npx -y rea-agents@${REA_VERSION} --version --json \
            > "$REPORT_DIR/rea-version.json"

      - name: Install application dependencies
        run: npm ci

      - name: Build known artifact
        run: npm run build

      - name: Hash build
        shell: bash
        run: |
          find dist -type f -print0 | sort -z | \
            xargs -0 sha256sum > "$REPORT_DIR/build-files.sha256"

      - name: REA static analysis
        id: rea
        shell: bash
        run: |
          set +e
          npx -y rea-agents@${REA_VERSION} \
            analyze-javascript-application "$GITHUB_WORKSPACE/dist" \
            --json --full-output \
            > "$REPORT_DIR/analysis.json" \
            2> "$REPORT_DIR/analysis.stderr"
          rc=$?
          echo "$rc" > "$REPORT_DIR/exit-code.txt"
          exit "$rc"

      - name: Upload diagnostics and evidence
        if: always()

        with:
          name: rea-analysis-${{ github.sha }}
          path: ${{ runner.temp }}/rea-report
          retention-days: 7

For stronger supply-chain reproducibility, pin Actions by full commit SHA after reviewing them rather than relying permanently on moving major tags. REA's own CI guidance notes that its sample pins action revisions and also distinguishes pinning the REA version from pinning all transitive npm dependencies; a committed lockfile plus npm ci is the stronger dependency-reproducibility model. 

Do not expose Brain Tunnel, production credentials, live NNTP credentials, NzbDAV credentials or other production secrets to this workflow. The static REA lane does not need them. 

Evidence confidentiality rules
REA itself warns that reports may contain paths, URLs, source-derived facts and caller-selected data, and says operators should review artifact access and retention rather than assume REA will infer secrets from their names. 

Apply these rules:

Never place production credentials in fixtures or Evidence. Replace NNTP usernames/passwords, API keys, auth headers, cookies, bearer tokens, private URLs containing credentials, NzbDAV credentials and Brain Tunnel details with deterministic placeholders before analysis.

Treat raw REA Evidence as potentially sensitive even when static. It can preserve paths, source facts, URLs and strings. Store raw output as internal-raw; commit only after automated and manual redaction review. 

Prefer repository-relative paths in index metadata. Absolute /home/... paths provide little analytical value and expose workstation identity. Preserve the original absolute path only in local raw evidence if REA requires it for provenance; REA's own Evidence records retain canonical/selected path identity. 

Synthetic data only for runtime tests. Use fabricated NZBs, fake Message-IDs, invented hosts and credentials, local-only test servers and temporary directories. Never store private NZB contents, actual Usenet article data or real media samples merely to make an architecture test realistic.

Logs are evidence, not dumping grounds. Redact headers such as Authorization, cookies, provider usernames/passwords, query-string API keys and filesystem paths with personal identifiers before committing. Preserve a redaction log containing the field and reason, not the removed value.

Hash originals before sanitization. Keep raw_sha256 locally and sanitized_sha256 in the commit index so later reviewers can establish that a sanitized record derives from a specific local original without publishing the original.

Keep CI artifacts short-lived by default. Seven days is a sensible initial diagnostic period; GitHub allows explicit artifact retention within repository/organization limits. 

Never interpret exit 0 as security clearance. REA explicitly says a successful operation can retain incomplete coverage, unknowns or limitations. 

Legal and licensing handling
REA 6.8.0 is distributed under MIT; Ghidra's primary license is Apache 2.0, with additional third-party components carrying their own licenses. Ghidra's user agreement also explicitly reminds users that reverse-engineering activity must itself be lawful and compatible with applicable software licenses. 

Those tool licenses do not determine the license of analyzed KaijuFlow/upstream source, bundled assets, dependencies, generated source maps, or evidence excerpts. Before committing generated evidence that embeds source text or third-party assets, verify the imported application's actual license files and third-party notices. This report does not independently establish those upstream licenses.

Tool choice and risk register
Why REA is retained rather than replaced
REA is being selected for a narrow problem that the alternatives do not cover as cleanly: independent reconstruction and provenance of the built JavaScript artifact. It records artifact identity, graph observations, coverage, explicit limitations and Evidence, and it can analyze a directory without running the target. 

It is not being selected because it is universally stronger than the alternatives.

The refined plan therefore keeps Stages 0–5 intact but changes their evidentiary hierarchy: Stage 1 source analysis defines the canonical architecture; Stage 2 REA independently witnesses the built artifact; Stages 3–4 establish behavior; Stage 5 establishes performance. Ghidra remains a conditional native-analysis tool. The evidence index links all four layers to immutable hashes and explicit claims, making it possible to audit exactly what was observed, by which tool, from which commit and artifact, with which limitations—without touching Brain production or requiring a PR merge.
