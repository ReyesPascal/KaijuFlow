## Expected settings (`expected-settings.json`)

The settings every test copy is expected to have are in `tools/brain/expected-settings.json`; the preflight compares each copy with it ([rules.md](rules.md#expected-settings-109)). Change the standard there and in the test copies together.

```json
{"about": "...",
 "expected": [
  {"copies": ["kaijuflow"],
   "settings": {"movieFilters": {"sortOrder": ["regexScore", "quality"], "maxFileSize": 32212254720},
                "tvFilters": {"sortOrder": ["regexScore", "quality"], "maxFileSize": 10737418240}}},
  {"copies": ["kaijuflow"],
   "settings": {"ultimateFallback.enabled": true}}
 ]}
```

(The example is cut short; the file holds both filter sections in full.)

A setting is named from the top of the copy's config down, with dots: a whole section (`movieFilters`) or one setting (`ultimateFallback.enabled`, `import.max_processor_workers`). Only the named settings are compared, and a named section must match as a whole, with nothing missing and nothing extra. AltMount's `config.yaml` is read with every value as text and list entries by position, so the preflight turns the AltMount copy's expected values into that form first (`0` is read as `"0"`, `false` as `"false"`, a list entry by its position rather than its `name`). `key: ""` is left out on both sides, because the reader skips it.

| Field | Meaning |
|---|---|
| `about` | what the file is, in plain words; not read by the tools |
| `expected` | the entries; each one names copies and the settings they must have |
| `copies` | the test copies the entry is for: `kaijuflow`, `altmount-kf` (the one setup, #187) |
| `settings` | setting name and expected value. The name is the setting's name in the run's `settings.json`: a top-level name (`movieFilters`) or a dotted one (`healthChecks.sampleCount`) |

- A value that is an object (a section) is compared as a whole: every value in it must match, and a value the copy has there and the file does not is a difference too. A list of plain values (an order) is one setting.
- The value is compared as the run's `settings.json` holds it. KaijuFlow keeps numbers and true/false. The AltMount copy keeps every value as text, so the preflight compares an expected `2` or `true` as `"2"` or `"true"`.
- The file is in the repository: no host, address, login or key. An entry whose setting has a secret name (the settings reader's own test, `brainreport.is_secret_name`) is refused.
- A file that cannot be used fails the preflight with one sentence that says why.

Today the file holds KaijuFlow's standard sort and filter rules, its fallback on with the Play-time check's settings (#190), and the dev switch on (`devDiagnostics`, #280: off in a release, on in the test copies only; [step lines](#step-lines-kf-step)); `ultimateFallback.userPickFallback` cannot be named, because the settings reader takes its name for a login, and KaijuFlow does not need it: with the Play-time check on a failed list entry always falls back; any other setting the settings reader reads, of KaijuFlow or its AltMount, can be added the same way.

**Applying it (#163).** `python3 -I tools/brain/testbed.py apply <copy> [--expected FILE]` writes every setting the file names for that copy (all its entries together) into the copy's config (`config.json`, or `config.yaml` for an AltMount copy), each named setting replaced as a whole, and leaves everything else as it was (it refuses to write when anything else would change). It reads the file as it is, so a change to the file is picked up with no change to the command. Before writing it copies the config to `<test folder>/backups/<copy>-<UTC time>-<file name>`. It prints, one line each, the backup, every setting that changed (`KaijuFlow: movieFilters.maxFileSize: 53687091200 -> 32212254720`; a setting, rule or section that was missing or extra as a whole is named once, as the preflight names it: `AltMount KaijuFlow: segment_cache.enabled: added, "true"`, `KaijuFlow: tvFilters.minFileSize: removed (was 5)`), and how many changed. Values are shown as the settings reader reads them, so no secret is printed. A copy that already holds the values gets one line, `<copy>: nothing changed; <config> already holds the expected settings.`, and no backup. A copy the file names nothing for, or NzbDAV (its settings are in a database), gets `Nothing applied: ...` and exit 1.

## The title draw and the ledger (`draw.py`)

Every real-use check plays new titles (ADR 0010, #269). `python3 -I tools/brain/draw.py titles --check "<check>" --kinds popular-film=3,popular-episode=2 --out <titles.json>` draws them from TMDB, with the metadata key it reads from KaijuFlow's test copy (`pool.tmdb_getter`) and never prints. It prints one line per title (`popular-film: Avatar Aang: The Last Airbender (tt18259538)`), then `done in N s`.

**Kinds.** A title is chosen by its kind only, never by hand and never by whether it will play:

| Kind | Type | Drawn from |
|---|---|---|
| `popular-film`, `popular-episode` | film, episode | TMDB's popular films, popular shows |
| `rare-film`, `rare-episode` | film, episode | older titles (films before 2000, shows first aired before 2005) or little-known ones (20 to 200 votes), one of the two at random |
| `foreign` | film | a film in another language (one of twelve, at random) whose English title is not its original one |
| `anime` | episode | Japanese animated shows |
| `remake` | film | well-known films that share their name with a real film of another year (TMDB's search finds it, with 50 votes or more) |
| `daily` | episode | English-language talk shows with a season of 100 episodes or more (one on most weekdays), an episode of the latest such season |

From each kind's list the draw takes a page of the first 25 (500 titles) at random and goes through it in random order. It skips a title in the ledger, a title without an IMDb ID, a film not released yet, and a show with no aired episode; an episode is a random aired episode of a random aired season. Each title's ID is checked against TMDB (`pool.check_title`); one that does not check is skipped. A kind that finds no new title in 8 pages is refused with one sentence, and nothing is drawn. `--kinds anime=1` draws one more title of a kind, a full check's replacement for a hard-case title with nothing to play.

**The title list** is `[type, id, label, kind, date]`, in the order of `--kinds`. The date is a film's release date or an episode's air date (TMDB's), so a check can tell the right title from another of the same name. It is a real-use check's list:

```json
[
  ["movie", "tt18259538", "Avatar Aang: The Last Airbender", "popular-film", "2026-07-24"],
  ["series", "tt7899522:1:30", "GeGeGe no Kitaro S01E30", "anime", "2018-10-28"]
]
```

**The ledger** is `~/kaijuflow-notes/brain-runs/titles-played.json` (`--ledger` names another), with the runs, outside the repo, backed up by `backup.sh`. It holds every title a check drew, a show once for all its episodes:

```json
{"about": "...",
 "titles": [
  {"id": "tt18259538", "type": "movie", "label": "Avatar Aang: The Last Airbender", "kind": "popular-film", "date": "2026-07-24", "check": "quick 2026-11-25", "when": "2026-11-25T10:00:00+00:00"}
 ]}
```

A drawn title counts as played. The ledger is written before the title list, so a check that stops, or a list that cannot be written, leaves its titles spent (the owner: "dont redo same things") and never lets a later draw take them again. `draw.py seed` adds the titles the replayed recording's speed tests played (Test 1's ten and the pool's used titles) once, with the kind `old process`, the check `replayed recording` and no date; it was run on 2026-11-24 (70 titles).

**The capture.** `test_draw.py` replays TMDB's real answers to one draw of every kind (`fixtures/2026-11-24-tmdb-draw/`). A change to the order of the draw's TMDB calls or its random picks needs a new one: `python3 -I tools/brain/test_draw.py --capture tools/brain/fixtures/<day>-tmdb-draw` (with the test copy's key, which it never writes), then point the test at it.

## Check folder

A real-use check (`brainrun.py check --quick`, #270; rules: [Real-use checks](rules.md#real-use-checks-270-spec-268-adr-0010)) writes a folder in the runs root, named `<start>-quick-check` (`--name` names another), and one INDEX.md row: result `pass`, `FAIL`, `NULL` (the cap rule) or `stopped`, the headline as the report's first line. It holds:

- `report.md`: the verdict and the fails first, then slow plays, check misses, fallbacks, nothing to play, the typical title to video and the indexer table (`quickcheck.indexer_rows`, #304), then a ticket text per fail and check miss.
- `titles.json`: the drawn titles, `[type, id, label, kind, date]` ([the draw](#the-title-draw-and-the-ledger-drawpy)).
- `raw.json`: `{"status", "visits", "outcomes"}`. A visit is what the check saw of one title: `title` (the five fields), `t_start`, `t_end`, `list_status`, `list_s`, `sources` (the list's Sources, the Best entry left out), `best`, `browse_pause_s`, `play` (the press of Best: `plays`, `first_byte_s`, `size`, `note`, ...; `null` when there was nothing to press), `steps` (KaijuFlow's `indexer_page`, `list_filter`, `list`, `play_check`, `played` and `play_failed` lines of the visit, [below](#step-lines-kf-step)), `found` (`{indexer: [release names]}` its `search` lines found, #304; `{}` with the dev switch off), `imports` (AltMount's), `limit`, and `cut_by_limit` (true on the visit the cap rule stopped: it is kept but not judged, so it has no outcome). An outcome (`quickcheck.judge`) is `outcome` (`played`, `fail`, `nothing to play`), `why`, `release` (the release played), `video`, `start_s`, `title_to_video`, `slow`, `fallbacks`, `check_misses` (`release`, `reason`), `checked` (`release`, `ok`, `status`) and `allowed_word` (#286: `word`, `where`, `release`, `video`, `proof`, the odd word a maybe that played the right title offers; `null` when none), with the title's `label`, `id`, `kind` and `sources`.
- `meta.json`: `kind` (`quick check`, or `drill-down`: [Drill-down](#drill-down)), `name`, `status` (`ok`, `null`, `stopped`, `failed`), `verdict` (`pass`, `fail` or `null`), `headline`, `started`, `finished`, `seconds`, `commit` (the image's), `head`, `dirty`, `altmount` (`image`, `id`: AltMount's test copy after the reset, #287), `titles`, `indexers`, `null`, `stopped`, `error`, `browse_pause_s`, `start_load`, `machine`. Checks are never judged against each other (ADR 0010).
- `settings.json` (the test copies' settings, secrets as `***`, from `testbed.read_settings`); `logs/`: the stand-in's log (its `RECORD` lines count in the allowance) and both containers' lines per title, scrubbed (`evidence.scrub`: keys, passwords and logins in links, and every secret value the test folder holds, `testbed.secret_values`).
- `evidence/`: one [evidence folder](#evidence-folder) per play that failed or fell back (#280); none for a play that went fine (a Drill-down keeps its one play's however it went). The play's outcome in `raw.json` names it (`evidence`: `evidence/01-the-witcher-s01e01`), or says why it could not be written (`evidence_error`).
- `diagnosis.json`: [Diagnosis](#diagnosis)'s summary of the check, when a play left an evidence folder.
- `fix-tickets/<entry id>.md`: the fix ticket of each proved KaijuFlow cause ([Fixing](#fixing), #288), filed unless the check was a dry run (`--tickets-dry-run`).

The stand-in's answers go to `<test dir>/check-answers/<folder>` while the check plays; a failed or fallen-back play's are copied into its evidence folder, then the store is deleted.

## The Speed Check page (`checkpage.py`)

`python3 -I tools/brain/checkpage.py <check folder> [<check folder> ...] [--out DIR]` writes `index.html` (default `~/kaijuflow-notes/brain-1338/page/`) from check folders' `meta.json`, `raw.json` and `logs/standin.log` and publishes nothing (#273, ADR 0010). The newest check given that has a verdict leads: its headline, its fails with why, its totals as its `report.md` gives them (titles, fails, slow plays, check misses, nothing to play, fallbacks, the typical title to video; no per-title table), and its indexer table, the rows of its `report.md`'s `## Indexers` (#312; `quickcheck.indexer_rows` and `indexer_cells`, shared with the report; a check from before #304 has no `list` steps or `found` in its `raw.json`, so its lists read 0 and its plays-only-it-had "not known"). Then "Every check so far": one row per check given, newest first, with its headline (a check with no verdict says why). A folder whose `meta.json` names no check kind (a timed run's) is refused in one sentence and nothing is written. Test: `test_checkpage.py`, on the quick check of 2026-11-24 (`fixtures/2026-11-24-quick-check/`).

## Evidence folder

What a failed or fallen-back play leaves for Diagnosis (#280, spec #279), written by one shared part, `tools/brain/evidence.py` (`evidence.save`), so the quick check, the full check and the Drill-down keep one format. Its place: `<run folder>/evidence/<NN>-<label>/`, `NN` the play's place in the check (`01`), `label` the title's label in lower-case words with dashes (`the-witcher-s01e01`). A play gets one when its outcome (`quickcheck.judge`) is a fail or nothing to play, it fell back (`fallbacks` above 0), or it was a slow play (`evidence.kept_because`); a play that went fine gets none, but in a Drill-down, whose one play always keeps its folder (#272; `kept_because` null). It holds:

- `evidence.json`: `format` (1; a reader refuses a format it does not know), `check` (the check folder's name), `kind` (`quick check`, `drill-down`), `title` (the draw's five fields), `label`, `id`, `kept_because` (`fail`, `nothing to play`, `fallback`, `slow play`; null for a Drill-down's play that went fine), `outcome` (the outcome as `raw.json` keeps it), `t_start`, `t_end`, `commit` (the image's), `head`, `dirty`, `altmount` (AltMount's test copy as it ran: `image`, `id`, from `docker inspect`; #287), `dev_switch`, `failed_sources`, `altmount_nzbs`, `answers` (below).
- `steps.jsonl`: every [step line](#step-lines-kf-step) of the play, one JSON object per line in log order: the title's own (`ref` its id) and those with no `ref`, from a second before the visit started; not only the ones `raw.json` keeps.
- `logs/kaijuflow-test.log`, `logs/altmount-kf-test.log`: both containers' lines for the play, as the check read them, scrubbed (`evidence.scrub`). `logs/standin.log`: the stand-in's request lines sent during the play (from a second before its start until the next play started, or its end plus the 5 s grace), scrubbed.
- `settings.json`: the settings of every test copy, secrets as `***` (the check's `settings.json`).
- `nzbs/<release>.nzb`: the NZB of every Source that failed, as the stand-in stored it; `nzbs/altmount/<name>.nzb`: AltMount's copy of a failed import, read from its test copy's `config/.nzbs/failed/<category>/` (the path its `Moved failed NZB to failed directory` line names; the one narrow exception the project guard allows, `guard.FAILED_NZBS`).
- `answers/<indexer>/<key>.body` and `.meta.json` (and `indexer.json`): the indexer answers the stand-in served during the play, in the store's own layout, so the Stand-in replays them: `indexer_standin.py --mode replay --store <evidence folder> --list answers`.
- `live.json` (#284): the [live Clues](#diagnosis)' answers, asked once right after the check: `t` (when), and `clues` (`{clue: {release: {answer, facts}}}`) for every failed Source whose NZB the folder kept (in `nzbs/`, or AltMount's copy named after the release); or `t` and `error` when the connection could not be opened. No file when no failed Source had an NZB kept.

| Field | Meaning |
|---|---|
| `dev_switch` | `setting`: KaijuFlow's `devDiagnostics` in `settings.json` was `true`; `step_lines`: how many of the play's step lines carry `dev: true`, `of`: how many it has. A folder made with the switch off (or with a build from before it) lacks the diagnostic lines and fields: never read it as complete |
| `failed_sources` | one entry per Source that failed, in the order it first failed: `release`, `failed` (`check`: its Play-time check did not pass, with its `status`; `play`: a `play_failed` line; `import`: a failed `import_wait`, in builds from before `play_failed`), `nzb` (its file in `nzbs/`, or null when no answer the play kept holds it) |
| `altmount_nzbs` | one entry per failed import AltMount moved: `from` (the path in its container), `nzb` (its file in `nzbs/altmount/`, or null when the file was gone) |
| `answers` | `list` (`answers`), `kept` (how many answers were copied), `not_stored` (the request lines whose answer the store did not hold: a `MISS`, an `ERROR`, a limit) |

## Diagnosis

What Diagnosis (#283, spec #279; `tools/brain/diagnosis.py`) makes of an [evidence folder](#evidence-folder), and the files it keeps. One call, `diagnosis.diagnose(<evidence folder>)`, answers every failure of the play; a quick check runs it by itself at its end when a play left an evidence folder (`diagnosis.after_check`), and `diagnosis.py diagnose <folder>` runs it by hand.

**The failures of a play.** None for a play that went fine (`kept_because` null: a Drill-down's). One per Source that failed for the play (an `evidence.json` `failed_sources` entry that is `play` or `import`: AltMount refused it, or it failed after its check), in the order they failed; a Source its Play-time check stopped is the check working, not a failure. A play with no such Source (nothing to play, a fail before any Source, a slow play) has one failure, the play's.

**The fingerprint**: `<kind> | <where> | <reason>`, for example `check miss | import_wait not ok | AltMount could not process the Source: {...all files failed validation...}`.

- `kind`: `fail` (no video), `wrong title`, `nothing to play`, from the play's outcome; when video came, a failed Source is a `check miss` when its Play-time check had passed it (a `play_check` line with `ok`), else a `fallback`; a play with no failed Source and late video is a `slow play`. A wrong-title play is a failure of its own beside its failed Sources, which are then check misses or fallbacks (video came, story 71).
- `where`: the failing step line and whether it was ok: the failed Source's first prepare step (`nzb_fetch`, `unscramble`, `upload`, `import_wait`, `first_byte`) that was not ok, else its last; for the play's own failure, its last step line, the list's own lines, the play's events and Kaiju Search's `search` lines (dev switch only, so the switch never changes a fingerprint) left out; a slow play's is the played Source's last step line (its `played` line's release, else the last whose `first_byte` was ok: the Walk can go on after it), and its reason is `most time in <step>`, the played Source's prepare step or `play_check` that took the most time (rules version 2). `none` when there is none.
- `reason`: the failed Source's `play_failed` reason, or, in builds from before #242, KaijuFlow's own failure line nearest its failing step (within 2 s: `❌ Failed: <reason>`, `❌ Stream failed [i/n] <release>: <reason>`); the play's own failure takes the outcome's `why`. Masked, then `-` when empty.

**The masking file**, `tools/brain/masking-rules.json`: `version` (a whole number from 1; raise it on any change), `never_a_sign` (what is never part of a fingerprint, replaced by its placeholder wherever the evidence names it, longest first: the `title` (the label, and a series' name without its episode), the `indexer` (every step line's `source`), the `release` (every release the play's steps and failed Sources name), the `job` id), then `masks` in order, each a `pattern` (a Python regular expression) and the placeholder it is replaced `with`, or `keep: true` (what it matches is left as it is and no later mask touches it: an HTTP or NNTP status code). Whitespace is folded to one space.

**Leads and proof.** Every Casebook entry ([casebook/README.md](../casebook/README.md)) whose `match` has a sign that fits the fingerprint (kind and step equal or `*`, the reason a pattern where `*` is anything) is a lead, most occurrences first. Each lead's `confirm` recipe runs on this failure's own evidence: `proved` (every Clue gave the recipe's answer), `ruled out` (a Clue gave the opposite yes or no), `can't tell`, or `no confirming test` (`none (no evidence kept)`, or a Clue not built yet, named in `why`). The answer: **found** when a lead is proved (`says`: `found: <id>, proved by Clues <names>`, and `also found: <id>` for each further one); else **suspected** when a lead could not be tested (`suspected: <id> (no confirming test)`, or `(its confirming test could not tell)`); else **new** (`new: no Casebook entry matches`, or `new: every lead was ruled out (<ids>)`).

**The Clue format** (`tools/brain/clues.py`, `CLUES`): a Clue is registered by name (lower-case words joined by `-`) with the one yes/no question it answers; it is a function `(evidence, failure) -> (answer, facts)`, `evidence` the folder as `evidence.read` gives it (`meta`, `steps`, `kf_lines`, `am_lines`, `settings`, `nzb(release)`), `failure` the failure above (`release`, `kind`, `step`, `where`, `reason`); `answer` is `yes`, `no` or `can't tell`, and `facts` are the lines and fields it saw, quoted as the evidence holds them (a log line whole, a step line as its fields), so a claim can be checked against the evidence. A Clue that raises answers `can't tell` with the error. Every Clue is tried in `npm run check:brain` on two real captures, the cause present (yes) and absent (no), and so is every recipe whose Clues are all built (`test_diagnosis.py`, `test_clues.py`). A Clue is never deleted.

**Live read-only Clues** (#284, `clues.LIVE`): a Clue that asks the provider about the failed Source's kept NZB, `(evidence, failure, usenet) -> (answer, facts)`, `usenet` one read-only connection (`nntp.Usenet`: pipelined STAT, and BODY checked in memory by `yenc.check` and dropped; nothing goes into a library, no Recording is written). At the end of a check with an evidence folder, before diagnosing, `diagnosis.live_clues` opens that one connection (only when some failed Source has a kept NZB; the provider is the test copy's AltMount's, `nntp.provider`), asks every live Clue once for each such Source, closes it, and writes each folder's `live.json`. The Clue of the same name in `CLUES` reads the kept answer (its first fact `asked live at <t>`), so a later diagnosis or a new masking version never asks again; a Source with no kept answer is `can't tell`. The live Clues: `articles-missing` (a STAT of every article outside the par2 files, in windows from 10 to 100, stopping once 10 have not answered 223, because each 430 costs the provider about 0.5 s; every miss asked again after the sweep; yes when one is 430 both times), `segment-crc-bad` (BODY of the first, middle and last article of the biggest file outside the par2 files; yes when one comes back with a size or CRC32 other than its `=yend`/`=ypart` lines name). Recorded answers for the tests: `fixtures/2026-11-24-live-clues/`.

**AltMount's raw answer for an import** (#284, `altmount-refused-import`): from KaijuFlow's log, AltMount's answer to the failed import (`AltMount answered KaijuFlow <code>: <message>`, the line nearest the failed `import_wait`, within 2 s); from AltMount's log, the Source's queue item (`Added NZB file to queue` naming `<release>.nzb`), its end (`Processing failed` with its `error=`, or `Successfully processed queue item`) and up to 5 of its WARN and ERROR lines with different messages, the noise in every import left out (`First segment has no data`, `subscriber channel full`, `Live heap is pressing`). The answer stops at the queue item's top-level error; the reason under it is in AltMount's log alone.

**`diagnosis.json`**, kept in each evidence folder: `folder`, `check`, `title`, `label`, `rules` (the masking rules' version it was made with), `failures` (each `release`, `kind`, `where`, `reason`, `fingerprint`, `leads` (each `id`, `sign`, `sign_rules`, `occurrences`, `status`, `whose`, `confirm`, `result`, `why` or `clues`: `clue`, `answer`, `facts`, `wanted`), `verdict` (`found`, `suspected`, `new`), `cause`, `proved_by`, `says`), and `earlier` (`rules` and `fingerprints` of every answer made with an older version). In the check's folder, `diagnosis.json` is the summary: `rules`, `counts` (`failures`, `new` (no lead fits), `matched`, `proved`, `unexplained` (not found), `suspected`, `unreadable`) and `plays` (`evidence`, `label`, `error` when the folder could not be read, `failures` with `release`, `kind`, `fingerprint`, `verdict`, `cause`, `proved_by`, `says`). It also holds `library` (the Clue library's names when the check ran, so the next check tells a reused Clue from a new one, #288), `fixes` ([Fixing](#fixing)) and `scoreboard` (below). With Case logs (#287) it also holds `cases` (each Case log the check opened or joined: `id`, `status`, `occurrences`, `new`), `open_cases` (how many Case logs under the cases folder have no Casebook entry yet) and `agent` (`started`: where the diagnosing agent runs, or `error`; `cases`). The check's `report.md` gets a Diagnosis section from it: the counts, open Case logs, one line per failure, one per proved cause's fix (Fixing, below), one per Case log, whether the diagnosing agent started, then the scoreboard.

**The scoreboard** (#288, story 58; `tools/brain/scoreboard.py`), `scoreboard` in the summary, the five numbers above plus four: `clues` (`ran`: the Clues this check's confirming tests ran; `since`: the last earlier check under the runs root that kept its `library`; `reused` and `new` (the names): those of `ran` in that library or not; `joined`: the Clues added to the library since; `library`: how many there are now; `since`, `reused`, `new` and `joined` are null when no earlier check kept a library), `fixes` (`proved_fixed`: the Casebook's entries `proved fixed`, this check's comebacks left out; `comebacks`: its entries `reopened` and this check's comebacks; `this_check`: this check's comebacks; `tickets`: the fix tickets this check filed), `by_cause` (the last 10 checks with a failure under the runs root and its `archive/`, oldest first, this one last: `check`, `failures`, `causes`, how many failures each proved cause had, `unexplained` for those with none) and `research` (over the Case logs: `count`, `used` (it shaped a hypothesis or a Clue), `logs`; null when no Case logs folder is kept). In the report: `Clues: the confirming tests ran 6: 5 reused, 1 new since the check <folder> (articles-missing); the library holds 11, 1 joined since (articles-missing).`, `Fixes: 1 proved fixed, 1 comeback in all; this check: 1 comeback (unscramble-read-error), 1 fix ticket filed.`, `Research: 3 looked up in 2 Case logs, 1 used.`, then one line per check, `- <folder>: 2 failures: unscramble-read-error 1, unexplained 1`. A check with no failure has the open Case logs and the scoreboard too, under `None: no play failed or fell back; open Case logs: N.` (after every check, spec #279, story 57), and writes no `diagnosis.json`.

**A new masking version.** `diagnosis.refingerprint(<runs root>)` (`diagnosis.py refingerprint`, and first thing after every check) finds every stored answer under the runs root and its `archive/` made with another version, fingerprints and diagnoses that play again with the current rules, keeps the old fingerprints in `earlier`, and writes the check's summary again. `caselog.refingerprint(<cases>)` (the same command, and after every check that keeps Case logs) does the same for every Case log made with another version, from its first occurrence's evidence: its `fingerprint` and `rules` new, the old ones in `earlier`, its id kept, so the same failure under the new rules joins it (a check finds a Case log by its fingerprint, story 25).

**Recording on the Casebook.** `diagnosis.py record <check folder>` adds, for every proved lead, the occurrence to that entry's `seen` (`check`, `title`, `play` the evidence folder, `date` the play's, `rules`), and for every ruled-out lead one line to its Ruled out section (the date, check, title and folder, the sign that fit, and each Clue that answered against the recipe), then writes the index again; nothing already there is added twice. A check does not record by itself, so the repository stays clean for the next check's preflight: record, then commit the entries and the index.

## Fixing

What a proved cause does after a check (#288, spec #279, stories 50 to 54; `tools/brain/fixing.py`). For every Casebook entry a lead was proved for in the check (`fixes` in the summary: `entry`, `title`, `whose`, `status` before the check, `fix`, `file`, `comeback`, `action`, `proved_in`, each play and Source it was proved on with `evidence`, `label`, `release`, `kind`, `date`, `commit`, `drill` and the `clues` that proved it), one `action`:

- **`ticket`**: a KaijuFlow cause whose entry is `open` or `reopened`, or `proved fixed` (a comeback). Its fix ticket's text goes into `<check folder>/fix-tickets/<entry id>.md`: the title `Fix: <the entry's title> (Casebook <id>)` (`Fix, a comeback: ...` for a comeback), the parent (the map, #183), the label `ready-for-agent`, the cause and what the viewer saw (from the entry), a comeback's earlier fix, its proof (each Clue of the recipe with its answer and its first fact, the evidence folder, the commit), the Drill-down command on the failed title (`python3 -I tools/brain/brainrun.py drill --title <imdb id> [--episode S01E02]`, #272) and the acceptance criteria. Unless the check is a dry run (`brainrun.py check --quick --tickets-dry-run`) it is filed (`gh issue create --label ready-for-agent`, then put under the map through the sub-issues API), once: an open ticket whose title holds `(Casebook <id>)` is named instead (`already`). `ticket` holds `title`, `file`, `filed` (`#123`, or null), `dry_run`, and `already` or `error` (the tracker could not be reached, or the ticket was filed but not put under the map).
- **`under way`**: a KaijuFlow cause whose fix is `fix in progress` or `fixed awaiting proof` (its Drill-down has not played yet): no new ticket.
- **`workaround`**: a cause that is AltMount's, an indexer's, Usenet's or `test-only`: the entry and its workaround (`fix`), no ticket.

A **comeback** is a failure that proves an entry that was `proved fixed`. The check leaves the Casebook alone (the next check's preflight refuses a dirty repo); `diagnosis.py record <check folder>` writes the fixes onto the entries: a comeback's entry becomes `reopened`, with a History line (`- <date>: reopened, a comeback: proved again in <check>, <title> (<evidence folder>); fix ticket #123. (Diagnosis, #288)`); a filed ticket goes first in the entry's `fix` (`#123 (fix ticket filed by Diagnosis)`), an `open` entry becomes `fix in progress`, and a History line says so. Nothing is written twice. A dry run's ticket changes no entry. An entry becomes `proved fixed` only through its Drill-down ([below](#drill-down), #272). `diagnosis.py fix <check folder> [--casebook DIR] [--dry-run]` diagnoses a check again with the Casebook as it is now (a Case log just written up as an entry) and makes its fixes the same way, keeping the rest of its summary.

## Drill-down

What a Drill-down (#272, spec #279; `tools/brain/drill.py`, rules: [The drill-down](rules.md#real-use-checks-270-spec-268-adr-0010)) keeps. Its folder is a [check folder](#check-folder) named `<start>-drill-down`, `kind` `drill-down`, its one play's [evidence folder](#evidence-folder) kept however it went, and its report the quick check's (`# Drill-down <start>`) with a **Drill-down** section after Diagnosis: one line per suspected entry, `- <id>: proved fixed: <why>.`, `- <id>: reopened: <why>.` or `- <id>: not marked <what it would be>: <why>.`. Its `diagnosis.json` summary holds `drill`:

| Field | Meaning |
|---|---|
| `check`, `date`, `label`, `evidence` | the drill folder's name, its play's date (`YYYY-MM-DD`), title and evidence folder (relative to the drill folder) |
| `suspects` | the entries to mark, each `entry` and `from` (the earlier evidence folders it was proved in, relative to the runs root; empty for one `--entry` named), the named ones first |
| `marks` | one per suspect: `entry`, `file`, `from`, `before` (its status before), `recipe` (its confirming recipe run on each failure of the play: `release`, `kind`, `result` as a lead's, `why`, `clues`), `result` (`proved fixed`, `reopened`, `not marked`), `would` (for one not marked: what it would have been, or null), `why` (`<title> played with no failure (<evidence>)`, `its cause was proved again on <release> by Clues <names> (<evidence>)`, `a new failure appeared: <release>: <says> (<evidence>)`, then for one not marked `; it has no fix to prove (fix: none yet)`, `; <would> claims proof, and it has no confirming test that runs`, or `no such Casebook entry`) |
| `error` | `the play left no evidence folder`, when it did not |

No `drill` when the drill had no verdict (nothing is marked; the report's section says so). `diagnosis.py record <drill folder>` writes the marks on the entries before the check's [fixes](#fixing): `proved fixed` or `reopened` as the status, and for every mark, one not marked too, a History line: `- <date>: proved fixed by the Drill-down <folder>: <why>. (Drill-down, #272)` (`reopened by the Drill-down`, or `the Drill-down <folder> did not mark it <would>`). Nothing is written twice. A KaijuFlow cause the drill proved again gets its new fix ticket from `diagnosis.py fix <drill folder>` after the record ([Fixing](#fixing): a `reopened` entry files one); the report says so.

## Case log

What Diagnosis keeps for a failure with no proved cause (#287, spec #279; `tools/brain/caselog.py`). At the end of a check, after diagnosing, every failure whose answer is not *found* (new, or suspected) opens a Case log, or joins the one with the same fingerprint (`diagnosis.open_cases`). The Case logs live in the notes repo, `~/kaijuflow-notes/diagnosis/cases/` (`brainrun.py check --cases` names another folder), one folder per log, `<kind>-<failing step>-<8 hex of the fingerprint>/`:

- `case.json`: the log, written only by `diagnosis.py case` (below) and by the check that opens or joins it, one writer at a time (`.lock` beside it: a second agent or a joining check waits, so no write is lost). `format` (1), `id`, `fingerprint`, `rules` (the masking version of the fingerprint), `earlier` (`rules`, `fingerprint`: the ones it had before a new masking version), `kind`, `where`, `reason`, `status` (`open`; `probable`: concluded, its recipe passed, not repeated at will; `proved`: concluded and repeated at will), `opened`, `occurrences`, `observations`, `hypotheses`, `clue_runs`, `attempts`, `research`, `tickets`, `asks`, `conclusion`, `entry` (the Casebook entry it was written up as, or null).
- `CASE.md`: the same, readable, written from `case.json` at every change.
- `<agent name>.log`: the diagnosing agent's output, when it ran outside herdr.

| Field | Meaning |
|---|---|
| `occurrences` | `n`, `evidence` (its evidence folder, relative to the log's folder), `check`, `label`, `release` (the failed Source, or null for the play's own failure), `date`, `rules`, `how` (`check`, or `repeat`: a Drill-down or replay that repeated it at will: a Drill-down's failure that joins a log already open is one by itself, a replay is added through `case repeat`; a Drill-down that opens a log is its first sighting, `check`). A conclusion's recipe runs on every occurrence added after it; a no on one opens the log again (#287 decision 7) |
| `observations` | `n`, `by` (`code` or `agent`), `t`, `occurrence`, `says`, `quotes`. Code writes, for each occurrence: the path (the play's or the Source's step lines in order, and the first that was not ok, its line quoted), what changed since the last quick check under the runs root that passed (the commit, AltMount's `image`, the settings, quoted from both folders), and each lead Diagnosis tried |
| `hypotheses` | `n`, `by`, `t`, `says`, `refuted_if` (the result that would refute it), `quotes`, `status` (`open`, `refuted`, `holds`), `result` (`says`, `quotes`, `t`) |
| `clue_runs` | `clue`, `occurrence`, `answer`, `facts`, `t`, `by` (`diagnosis`: a lead's recipe; `code`: every Clue in the library, run once on each new occurrence; `agent`). A Clue is run on an occurrence once, never again |
| `attempts` | `n`, `by`, `t`, `occurrence`, `ran`, `skipped` (asked again, not run), `next` (`do`: `research`, `clue`, `ticket`, `owner`, `capture`; `what`) |
| `research`, `tickets`, `asks` | `question`, `source`, `found`, `used`; `ref` (`#123` or a link), `fact` (what KaijuFlow should record); `kind` (`live go` or `login`: only what only the owner can give), `what` |
| `conclusion` | `hypothesis`, `title`, `saw`, `cause`, `whose`, `step`, `recipe` (`clue`, `answer`), `quotes`, `passed_on` (the occurrences its recipe passed on), `result` (`probable`, `proved`), `against` (a repeat its recipe said no on: the log is open again) |

**The claim check.** Every quote is `{occurrence, file, text}` (a file in that occurrence's evidence folder), `{occurrence, clue, text}` (a fact that Clue gave on it) or `{occurrence, check, file, text}` (a file of another check's folder in the same runs root); its text, at least 10 characters that are not spaces, is looked up whole with spaces folded. A write whose quote is not there, an observation, hypothesis, result or conclusion with no quote, a hypothesis with no `refuted_if`, an ask that is not a live go or a login, a pause with no `next` or with fewer than two hypotheses, and a conclusion whose hypothesis does not hold, with another still open, or whose recipe says no on an occurrence (or passes on none), are refused, and nothing is written.

**The commands**, `python3 -I tools/brain/diagnosis.py case <command> [--cases DIR]`: `list`; `show <id>` (`CASE.md`); `run <id> <clue>... [--occurrence n]` (each Clue on each occurrence it has not run on); `add <id> <file.json|->` (one write: `observation`, `hypothesis`, `result`, `research`, `ticket`, `ask`, `pause`, `conclude`); `repeat <id> <evidence folder>` (the folder must hold a failure with the log's fingerprint); `entry <id> <entry id> [--casebook DIR]` (a concluded log written up as a Casebook entry: its fingerprint as the sign, its recipe, `seen` the occurrences the recipe passed on, Ruled out the refuted hypotheses and ruled-out leads, How it was proved saying probable or proved; the format is checked and the index written again; commit both through review).

**The diagnosing agent.** When a check leaves an open Case log, it starts the agent by itself (`caselog.start_agent`): inside herdr, a `claude` agent in a new pane of the workspace's `agents` tab (made when missing), prompted with the routine, [diagnosing-agent.md](diagnosing-agent.md); outside herdr, `claude -p` detached, its output in the cases folder. Then the owner is told in one line through the usual alert (`kf-alert`): `Diagnosis: <n> failure(s) in <check> has no proved cause; the diagnosing agent is on Case log <ids> (<where it runs>).`, or that it could not start.

## Step lines (`[KF-STEP]`)

KaijuFlow writes one line per timed step to stdout (`src/utils/stepTiming.ts`): `[KF-STEP] ` followed by a one-line JSON object. `docker logs -t` prefixes are fine: parse from the first `[KF-STEP] ` (`json.loads(line.split("[KF-STEP] ", 1)[1])`). Lines carry names, titles and numbers only, never URLs or keys.

| Field | Meaning |
|---|---|
| `step` | `indexer_page`, `play_check`, `nzb_fetch`, `unscramble`, `upload`, `import_wait`, `first_byte`, the play's two events `played` and `play_failed` (#242, `ms` 0), and the list's own lines `list`, `list_filter`, `list_sort`, `list_build`, `fallback_group`, `head_start` (#249, below); Kaiju Search's `search` (#285, dev switch only, below); run folders from before #191 also hold `health_batch`, the list-time check's batch, which KaijuFlow no longer writes |
| `source` | Source or indexer name (none for an old `health_batch`) |
| `ms` | whole milliseconds the step took |
| `ok` | false when the step threw (the line is still written) |
| `t` | end time, ISO UTC |
| `ref` | Stremio id (`tt0133093`, `tt1234567:1:2`) of the title asked for; written on every step since #206 (the Head start's steps run while the list is open), read only on the search-side steps (`indexer_page`, an old `health_batch`) and the list's own lines |
| `title` | release title of the Source, on the prepare-side steps (`play_check`, `nzb_fetch`, `unscramble`, `upload`, `import_wait`, `first_byte`) and the play's events |
| `job` | Backend job id on `upload`, `import_wait`, `first_byte` |
| `dev` | `true` on every line while the dev switch is on (`devDiagnostics`, #280: off in a release, on in the test copies); absent with it off, so the lines are exactly a release's. Every diagnostic line and field added for Diagnosis (spec #279) is written only with it on |
| extras | `page` (`indexer_page`, 1 = first page); `count`, `checked`, `indexers` (an old `health_batch`); `result`, `parts`, `wait_ms`, `retry` (`unscramble`; `wait_ms` is the part of `ms` spent waiting for its turn, #119; a read-error is retried once and the retry writes a second line with `retry: true`, #245); `includes_upload` (`import_wait` on AltMount: one request uploads and waits, so there is no `upload` line); `status` (`play_check`: the health check's answer, `verified`, `verified_stored`, `blocked` or `error`; one line per Source the Play-time check checked, #190); `reason` (`play_failed`: why the Source failed for the play, KaijuFlow's words without an address or file path) |

**The list's own lines (#249).** Every Stream list request writes, in this order: `list_filter` (dead marks and the user's filters, the sort left out; `results` in, `kept` out), `list_sort` (the sort), `fallback_group` (writing the list's fallback group, which saves every group held to `config/fallback-groups.json`; `candidates`, and `groups` held after it), `list_build` (building the Streams, the group write inside it; `streams`), `head_start` (the part of starting the Head start that runs before the answer), then `list`: the whole request, from reaching the handler until the answer was handed back, with `cache` (`hit`: from the search cache, a warm list; `miss`: searched), `streams`, and a trace of the whole process meanwhile (`src/utils/processTrace.ts`): `cpu_ms` (process CPU, user and system), `gc_ms` and `gc_n` (garbage-collection pauses), `loop_max_ms` and `loop_p99_ms` (event-loop delay, sampled every 2 ms), `elu` (event-loop utilization, 0 to 1), `heap_mb` (heap in use at the end). The trace is the process's, so other work at the same time (a Head start's checks, a play) is in it. `list` is written one turn of the loop after the answer, never before it. A cold list writes no parts when its search fails; an empty list writes the parts it reached. `collect_visit` keeps them by `ref`, and stores beside them the runner's own CPU readings over the list request (`list_cpu`: `kaijuflow_ms` and `altmount_ms`, each test container's CPU by its cgroup, `machine_ms`, the whole machine's from `/proc/stat`, every core added up). The report's "The list's own work" shows both, per round and for every warm list (`brainreport.list_work_section`).

**Kaiju Search's lines (#285, dev switch only).** With `devDiagnostics` on, a cold list's search writes `search` lines (`ms` 0, `title` the title's name, not a release's), after its `indexer_page` lines:
- one per indexer and way of asking: `source` (the indexer, or `EasyNews`), `way` (`id` or `name`), `asked` (the IDs it was asked by, `imdb`, `tmdb`, `tvdb`, `tvmaze`, the ones its caps list that the title has; or `["name"]`), `count` (results that came back that way: the kept ones and those Search Flow's name filter dropped), `kept`, `sure`, `maybe`, and `results`, each `{release, flow, why}` with `flow` `sure`, `maybe` or `dropped` and Search Flow's why (the dropped ones last); a maybe that extra proof made sure (#286) has `proof` (`id`, `runtime`, `size`, `other name`) and a why that names the proof, then the name's own why after `by its name alone:`. An indexer asked by name only writes no `id` line. A release found both ways is on both lines and listed once. With Prowlarr or NZBHydra, a name query goes to several indexers at once, so what its filter dropped is on a `name` line of the index manager (`Prowlarr`, `NZBHydra`);
- `strict_alone: "nothing"` (no `source`) with `kept`, `sure` and `maybe`, when the search kept Sources and the strict rule alone would have left none of them (`sure` counts those extra proof made sure, #286; it is 0 when none).

**Search Flow's extra proof on the play's lines (#286, dev switch only).** A `play_check` line carries `video`, the name of the video file the check picked inside the NZB (loose videos; none for an archive): a maybe whose file fits the title is sure from then on (`proof` `nzb video`). A `played` line carries the Source's `flow` (`sure`, `maybe`), its `proof` when extra proof made it sure, and `video`, the name of the file played. The quick check reads `video` to tell the right title of a maybe and to offer its odd word ([Real-use checks](rules.md)).

They are the search's evidence: the evidence folder keeps them with the play's other lines (`steps.jsonl`).

**The play's two events (#242).** `played`: a Source's video is served to the player, written once per press (a Range probe or seek of the same entry within 15 s writes none), whether the Source was prepared for this press, by its Head start (#206) or for an earlier press (the Stremio dedup cache). `play_failed`: a Source failed for the play (a clicked list entry, or Best's Walk handing it to the Backend, in a Head start too), with `reason`; the play then goes on to the next Source or shows the failure video. A Source that is still preparing when the play moves on (the first-Source switch at 25 s, #192), or a stopped Head start, writes neither. These lines are the brain tools' only reading of a play in KaijuFlow's log: `brainreport.read_play(text, visit)` gives the visit's `played_source`, the title on its first `played` or `play_failed` line (the first Source KaijuFlow tried for the play, the one played unless it fell back), and `cause`, the reason on its first `play_failed` line, both stored in `raw.json` by `collect_visit`. A line counts for the visit from its start on, unless it names another title's `ref`. A run from before #242 is read from its stored `raw.json`: its logs hold no such lines and are not read again.

`brainrun.py` ties lines to a title like this: search-side lines by `ref`, for that side's visit until the next visit that used the same KaijuFlow container starts (a late `health_batch` is kept); prepare-side lines to the visit's top pick (`played_source`, above; else its release title in the played Stream's text), so background work of the previous title cannot land in the next one. The play's events are no steps of the visit. This runs once at the end of the run (`finalize_steps`).
