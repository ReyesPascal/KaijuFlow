# Brain tools: rules and settings

The cap rule, the preflight, the settings table, the expected settings, like for like, the replay wait, the indexer allowance and how the targets are judged. Back to the [runbook](../RUNBOOK.md) or the [index](../README.md).

## Cap rule

**Cap rule.** The first "limit reached" from any indexer aborts the run at once: the stand-in's `LIMIT_REACHED.json` (found at the start or after any visit), or a limit line in a side's own logs. The log wordings matched are the ones the sides print (`brainreport.LIMIT_RE`): the indexer's "Request limit reached" text as AltMount and KaijuFlow pass it on, `HTTP 429`, Usenet Ultimate's "Status: 429", KaijuFlow's "Failed to download NZB from X: 429" and the stand-in's `LIMIT_REACHED indexer=`; loose phrases such as "api limit" are not matched. The run is recorded as NULL in INDEX.md with the indexer and time, its report holds no numbers, and a null run is never used as the "previous run" for a diff. The stand-in and the test copies are stopped. A replay run ignores a marker older than its own start (replay never contacts an indexer, so an old marker was left by an earlier command and cannot be news); it is not deleted.

## Settings table and preflight (spec #72, ticket #74)

**Settings command.** `python3 -I tools/brain/testbed.py settings [--limit 100]` prints every test copy's settings as a table and the connection budget (per copy, total, provider limit), read straight from the copies' config files (KaijuFlow and Usenet Ultimate `config.json`, NzbDAV's database, each AltMount's `config.yaml`). Keys, logins and passwords are never printed. It replaces the hand-written table in SETTINGS.md. The run record's `settings.json` comes from the same reader (`testbed.read_settings`), so the table and the "what changed" list agree. The connection budget counts the NewsHosting login only: health-check cap (KaijuFlow, Usenet Ultimate); for NzbDAV and AltMount every provider entry on the same Usenet host as the copy's main provider, backup flag or not. An entry on another host (NzbDAV's backup login) has its own limit: it is shown beside the count (`+ other host max N, own limit`) and not counted.

**Preflight.** `python3 -I tools/brain/brainrun.py preflight [--for run|record] --store <store> --list <list> [--rebuild-image] [--provider-limit 100] [--key-file PATH]` prints one plain sentence per problem and exits 1, or exits 0 with `Setup is right ...`. `--store` and `--list` are only needed for `--for run`. `brainrun.py run` starts with the same check and stops before creating a run folder when it fails. Checks:

1. the `kaijuflow:test` image holds the code of the repository's commit and the tree is clean. The image's `kaijuflow.commit` label names the commit it was built from; the image is current when that is the repository's commit, or when no build input differs between the two (`git diff --quiet <image commit> HEAD -- <build inputs>`). So only a commit that changes the code in the image asks for a rebuild; a commit that touches only docs, tools or tests does not. The build inputs are listed once, in `brainrun.BUILD_INPUTS`: what the `Dockerfile` copies into the image, plus the `Dockerfile`, `.dockerignore` and `.gitattributes`, which can change what a build sees (the repository has no `.gitattributes` today, but one would steer the `git archive` the image is built from, so it stays on the list); a test holds the list in line with the `Dockerfile`. An image without a label, or from a commit the repository does not have, is not current. `--rebuild-image` builds an image that is not current from the commit itself, an archive of `HEAD` piped into `docker build --label kaijuflow.commit=<commit> -t kaijuflow:test -`, so untracked or ignored files can never get into an image whose label names that commit; it never builds from a dirty tree and leaves a current image alone;
2. record only: the key file (default `<test dir>/indexers.json`) exists, is readable only by the owner, and names exactly the indexers switched on in every test copy (only the names are read, so per-indexer settings added later are fine);
3. every indexer address in every test copy (also switched-off ones, plus Easynews or Prowlarr when on) is `http://host.docker.internal:1340/<slug>` with or without `/api`;
4. the caps add up to at most the provider limit (default 100). Each test Backend (NzbDAV and both AltMounts) is capped at 25 connections, and KaijuFlow's and Usenet Ultimate's health checks at 12 each, so the copies hold 99 together (the settings of the 2026-11-13 baseline); the preflight checks the sum, not the 25;
5. every test copy has the sort and filter settings of the expected settings file `tools/brain/expected-settings.json` (see [Expected settings](#expected-settings-109) below);
6. the stand-in's port 1340 is free;
7. run only: the recording `<store>/<list>/<slug>/` holds at least one answer for each switched-on indexer, and its state file `<store>/<list>/RECORDING.json` (written by the record command) says `complete`; for a recording that stopped early or is `incomplete` (the proof replay missed requests) the preflight says why and gives the record command to top it up.

Indexers are compared by the slug in the indexer stand-in's address, because each copy names them its own way (for example `IndexerOne` in one copy and `indexerone` in another). Every sentence is plain: the key-file fix reads "make the key file readable only by you (run: chmod 600 <path>)", and "the indexer stand-in" is explained once, in the first address sentence. The tools carry no indexer names. The run record's `commit` is the image label (the code that ran); its `head` is the repository's HEAD, which is a later commit after a docs-only change.

**For the record command (#75).** Call `brainrun.preflight('record', cfg, io)` (or `'run'`); it returns a list of sentences, `[]` meaning go, and `brainrun.preflight_command(mode, cfg, io)` prints them and returns the exit code. `cfg` needs `test_dir`, `store`, `listname`; optional `limit`, `standin_port`, `key_file`, `rebuild_image`. `io` is the runner's IO object (`RealIO`) and needs `git_info`, `image_label`, `build_inputs_changed`, `rebuild_image`, `setup_report`, `key_state`, `port_free`, `recording`; `FakeIO` in the tests shows the shortcut (`io.preflight(mode)`). The image decision alone is `brainrun.image_state(label, head, inputs_changed)`: `current`, `stale`, `unknown` or `missing`. The settings comparison alone is `brainrun.setting_differences(expected, settings, file)`: the entries of the expected settings file (`brainrun.load_expected_settings(path)`) and the settings reader's output in, sentences out; `cfg['expected_settings']` names another file than the committed one (the tests use it). Tests: `test_settings.py`, `test_preflight.py`.

## Expected settings (#109)

**Why.** The 2026-11-13 baseline ran on test copies that had lost their sort and filter rules, and nothing noticed: on KaijuFlow and Usenet Ultimate every film's top pick was a 66 to 91 GB file. The old rules could not be recovered, so the owner defined standard ones in issue #109, and the preflight now holds every copy to them.

**The file.** `tools/brain/expected-settings.json` ([format](formats.md#expected-settings-expected-settingsjson)) holds, for KaijuFlow and Usenet Ultimate alike, the whole `movieFilters` and `tvFilters`: KaijuFlow's default sort and filter object, plus the largest single file (`maxFileSize`: 30 GB for films, 10 GB for episodes, written in bytes) and the drop rule "No disc images". AltMount direct has no such rules; the file holds it to its own like-for-like settings instead (one try, 4K first: see [Like for like](#like-for-like-142)). NzbDAV and AltMount under KaijuFlow have no ranking of their own, so the file does not name them. The file is in the repository, so it holds no host, address, login or key; an entry with a secret name is refused. To change the standard, change the file and both test copies together.

**The comparison.** Both sides are read the same way (`testbed.read_settings`, the reader behind the settings table and `settings.json`), so no secret can reach a sentence. For every setting the file names, the copy must hold exactly the file's value. A setting given as a whole section (`movieFilters`) is compared as a whole, both ways: a value that differs, a value the copy lacks, and a value the copy has and the file does not are each a difference. KaijuFlow uses `movieFilters` and `tvFilters` in place of its default rules as a whole, so an extra or a missing value there changes the ranking. One sentence per difference:

```
KaijuFlow has movieFilters.maxFileSize set to 53687091200, but the expected settings file (tools/brain/expected-settings.json) says 32212254720: change the test copy's config, or the file if the copy's value is the intended one.
Usenet Ultimate has no tvFilters setting, but the expected settings file has one.
KaijuFlow has a movieFilters.minFileSize setting that the expected settings file does not have.
KaijuFlow has movieFilters.sortOrder entry 2 set to "size", but the expected settings file says "quality" (the first entry that differs).
```

- The first sentence names the file and says what to do; the others stay short.
- An order (`sortOrder`, `resolutionPriority` and the like) is one setting: one sentence names the first entry that differs.
- A section or a rule that is missing as a whole, or that only the copy has, is named once, not once per value in it.
- A copy whose config cannot be read is left to the checks that say so. A file that cannot be used costs one sentence (`The expected settings file cannot be used (expected-settings.json, entry 1: ...): fix the file.`) and the preflight fails.

**The size cap and the report's Size column are two figures.** `maxFileSize` is compared with the size the indexer gives for the post, the figure a Stream shows after the disk sign, which KaijuFlow counts in GB of 1024 x 1024 x 1024 bytes (`src/addon/filters.ts`, `src/parsers/metadataParsers.ts`). The Size column of the per-title table is the size of the served file in GB of 1000 x 1000 x 1000 bytes. So a top pick of 31 GB in the report can be inside the 30 GB cap.

## Like for like (#142)

**Why.** The 2026-11-13 baseline compared different things. AltMount direct had no scoring, so it sorted every list by newest post and picked 1080p files of 3.5 to 15 GB, while the other two picked 4K remuxes of 65 to 90 GB. And it ran with `stremio.max_fallback_releases = 2`, so a failed top pick quietly fell back to the next release (36 of 40 on first tries, not 40). The owner decided (2026-11-15) that every side plays by one rule set.

**What every side shares, and where each rule is held:**

| Rule | KaijuFlow, Usenet Ultimate | AltMount direct | Held by |
|---|---|---|---|
| The same Sources: no post over 30 GB for a film or 10 GB for an episode, no disc images, the first 100 results, no later page | the stand-in, and their own `maxFileSize` and "No disc images" rule as before | the stand-in | `indexer_standin.py` when it serves an answer |
| 4K first: 2160p, then 1080p, then 720p | `resolutionPriority` (KaijuFlow's default sort) | `stremio.scoring.custom_formats`: 2160p 400, 1080p 300, 720p 200, and "4K words beside 1080p or 720p" -400 (#154) | the preflight, against `expected-settings.json` |
| One try per play: no hidden fallback | `ultimateFallback.enabled = false` (already so) | `stremio.max_fallback_releases = 0` and `stremio.include_library_streams = false` | the preflight, against `expected-settings.json` |
| The same indexer and Backend connections | one indexer (NinjaCentral); 25 connections per Backend | the same | the preflight's address and connection checks |

**The stand-in's list.** Every search answer (`t=search`, `movie`, `tvsearch`) goes out filtered, in record and replay mode alike. The answers stored on disk stay as the indexer sent them, so a later change to the rules needs no new recording.

- *Kind.* A search with `t=tvsearch`, or with TV categories only (`cat=5000`, ...), is an episode search; any other search is a film search.
- *Size cap.* A post over the cap of its kind is dropped: `maxFileSize` of `movieFilters` (films) or `tvFilters` (episodes) in the KaijuFlow entry of `expected-settings.json`, the one source of both figures. The size is the post's newznab `size`, else its enclosure length, in bytes, as KaijuFlow compares it. In an episode search a post whose title names no episode (no `S01E02` or `1x02`) is a season pack and has no cap, because KaijuFlow's `maxFileSize` leaves season packs alone too (`src/addon/filters.ts`).
- *Disc images.* A post whose title matches the "No disc images" rule of that same entry is dropped. The pattern is read from the file, not copied.
- *The first 100.* Each answer is filtered on its own, and the first 100 posts left in the indexer's order are kept. A search for a later page (`offset` above 0) gets an empty answer at once, in the format asked for (XML, or JSON for `o=json`). It is not stored, not sent to the indexer, never a miss, and logged `EMPTY <slug> <request>`. So KaijuFlow's paged search and AltMount direct's single `limit=100` request both choose from the indexer's first page, filtered the same way. KaijuFlow stops paging when a page comes back empty, so it loses pages 2 to 4 in the test.
- *Not equal yet.* Each side still sends its own query (KaijuFlow searches by title text, AltMount direct by IMDb or TVDB ID), so the indexer can answer them with different posts. This ticket makes the rules equal, not the queries.

**AltMount direct's settings.** AltMount matches on release titles only, so it cannot cap a file size; the stand-in does that for it. The rest is in its `config.yaml` under `stremio`, and the expected settings file holds the values: `max_fallback_releases: 0` (one import per play), `include_library_streams: false` (no redirect to a file already imported), and `scoring.custom_formats` for 2160p, 1080p and 720p (400, 300 and 200) plus "No disc images" (the #109 pattern with `(?i)` in front) scored -10000: AltMount drops a release that matches any format scored -1500 or less. AltMount adds up the score of every enabled format a title matches (`internal/stremio/scorer.go`, `EvaluateRelease`, v0.4.0), and the 2160p format also matches the words 4K and UHD, so "Inception 2010 PROPER 1080p UHD BluRay" (a 1080p encode from a 4K disc) scored 400 + 300 = 700 and beat real 4K: in Test 1 AltMount direct played 1080p on 7 of 10 titles (#154). The format "4K words beside 1080p or 720p" (4K or UHD with a stated 1080p or 720p, in either order) scores -400 and takes the words' 400 back, so a release scores by its stated resolution: 400 for 2160p, 300 for 1080p, 200 for 720p, and 400 for 4K or UHD with no number stated. AltMount's regexes are Go's RE2, which has no lookahead, hence a format of its own rather than a narrower 2160p pattern. Its settings are read like the other copies' (`testbed.read_settings`), one sentence per difference. Sources for each AltMount setting (v0.4.0): `~/kaijuflow-notes/research/altmount-scoring-v0.4.0.md`. `stremio.fallback_timeout_ms` is the indexer search timeout, not a fallback, and `stremio.max_retries` is read by nothing, so neither is held.

**Applying it.** Applying the settings to the test copies is a live change and the owner's go (at the start of #127). It is listed in the [runbook](../RUNBOOK.md), step 2.

### First-try plays and like for like per title (#143)

**A top pick plays on the first try only.** A visit counts as played when video arrived and the top pick's own import did not fail (`brainreport.plays`). The top pick's import is found by release name in the visit's `imports` (KaijuFlow's own log name, or the side's list text; NzbDAV's `.nzb` and AltMount's 16-hex tag are dropped); when no name matches, it is the visit's first import, except for KaijuFlow, whose log names its pick. KaijuFlow and Usenet Ultimate also queue the next two Sources of the list, so a failed import of one of those is no fallback. A visit whose video came after the top pick's import failed is a **fallback**: not played, shown apart as "played after N fallbacks" (N = the visit's failed imports) in the report's Fallback column and Result, and in `check`. The targets, the report, `check` and the Speed Check page all count this way. The 2026-11-13 baseline gives AltMount direct 36 of 40 (Chernobyl S01E02 fell back in every round).

**Like for like per title.** For every title and round, KaijuFlow's top pick is compared with each other setup's (not KaijuFlow's one-page variant). The pair is not like for like when the two picks state different resolutions (`brainreport.resolution`, #154: 2160p, 1080p or 720p, read from the name or list text; a stated number wins over the words "4K" and "UHD" (2160p) and "FHD" (1080p), which count only when no number is stated, so "1080p UHD BluRay" is 1080p. A side's own label in its list text ("AltMount FHD - Inception (2010) [1080p]", Usenet Ultimate's "4K BluRay") does not beat the release name, nor the other way round: the label and the name are read as one text and the first stated number wins. A side's label is its own reading of the same release name, and Usenet Ultimate's list text holds no release name at all, so there is nothing to prefer it over), or when either served file breaks the rules above: a disc image, or a file larger than the cap of its kind (the served file is never larger than its post, so a file over the cap means the post was over it; a season pack has no cap). Two files of one resolution inside the cap are like for like, whatever their sizes (owner, 2026-11-15). Such a title is named in the report's "Like for like" section and in `check`, with the first round that shows it, and left out of every target held against that setup (the target's "This run" says how many titles were left out). Targets with a fixed limit keep every title. Below those lines `check` prints a table of every title's top pick per setup in the first round (#154): the resolution read by this rule and the size of what was played (the served file, else the size its list states, "listed"), so a misreading shows the moment a run ends.

## Fails and title to video in a speed test (#167)

**One try for every setup.** Every setup gets one try per title, with no retries for anyone ([ADR 0007](../../../docs/adr/0007-speed-tests-play-as-at-home.md), amended): AltMount direct keeps its fallback off, KaijuFlow and Usenet Ultimate show the failure video.

**A fail** is a title whose top pick does not play on that try: no video, the failure video, a refusal, or video only after a fallback (the top pick did not play on the first try: [First-try plays](#first-try-plays-and-like-for-like-per-title-143)). A fallback shows as "played after N fallbacks"; with the expected settings it should not happen. Each play counts on its own: a warm play that works because a setup learned from a cold fail is a warm play, and the cold fail stays a fail. The report and `check` count fails per setup, round and list. As in the plays figure, a top pick that failed only because a request was not recorded is left out (such a run is not usable anyway).

**Title to video** is one clock from asking for the title until video: the visit's list time plus its start time, the same for every setup, so checking before the list and checking at play time cost the same. A fail has none. Its median is taken per setup, phase (both rounds of it together) and list, over the top picks that played. List and start times stay as detail. A run without tags is counted and reported as before ([formats](formats.md#run-folder)).

## Never compared with (#153)

**A run marked never compared with** (`"never_compared": true` in its `meta.json`, with its readable name in `"label"`) is like for like and stays in the runs root, but no later run is compared with it: it is never the previous run of a diff, a short run's baseline or the run the page compares with, and `check` says it is not usable as a baseline. Its page still builds from it alone, and the page and report call it by its label. Test 1 (`2026-11-15T115540Z-baseline`, the owner's decision of 2026-11-15) is the first so marked.

## Recording and the cap rule

**Cap rule for recording.** The first "limit reached" stops the pass at once; the recording is NULL: what was stored stays, the stand-in's `LIMIT_REACHED.json` stays in the store, the record pass gets an INDEX.md row `NULL` and the command exits with 2. A marker left by an earlier command never blocks a later one: a new `record` moves it aside (kept, renamed `LIMIT_REACHED.<its time>.json`) and goes on from what is stored; if the limit still holds, the first answer writes a new marker and the pass stops as before.

**Replay wait.** By default the stand-in waits the recorded indexer time for every replayed answer (#73), so list times look like real life. `run --no-wait` switches that off for a tuning run; the run record notes it as the run-level fact `stand-in replay wait: on|off` (in `meta.json`, not in the settings snapshot), so "What changed since the last run" shows it.

## Indexer allowance (spec #77, ticket #87)

**Limits file.** `limits.json` sits next to the key file (default `~/kaijuflow-test/limits.json`, outside the repo; you fill it in once). Example: `tools/brain/limits.example.json`.

```json
{"indexers": {"ninjacentral": {"search_per_day": 2000, "download_per_day": 450, "reset": "rolling-24h"}}}
```

- `search_per_day`: the daily limit of search (API) requests. `download_per_day`: the daily limit of NZB downloads. Whole numbers.
- `reset`: `"rolling-24h"` (the last 24 hours count; NinjaCentral's reply carries no usage fields and the reset is not confirmed, so this is the safe reading) or a clock time such as `"04:00"`, read in UTC unless the entry also has `"timezone": "Europe/Berlin"`.
- The name is matched to the stand-in's indexer name and the copies' names ignoring case, spaces and dashes.

**`python3 -I tools/brain/brainrun.py usage [--key-file PATH] [--test-dir DIR] [--runs-root DIR]`** prints, per indexer, `Used`, `Limit` and `Left` for searches and for downloads since the indexer's last reset. Used adds up two things: the stand-in's real requests in the record folders (`RECORD` and `ERROR` lines of each `logs/standin.log`; `api` is a search, `nzb` is a download; replayed `HIT` lines cost nothing) and the counts the live copy keeps (`queryHistory` and `grabHistory` in its `config/stats.json`, read-only). The test copies are not counted: they only talk to the stand-in, so their counters never measure real indexer hits. A copy keeps only its latest hundred entries of each, and the command counts this machine only; it says so. Without a limits file it prints one sentence asking you to fill it in. It never contacts an indexer. Code: `allowance.py`; tests: `test_allowance.py`.

**`preflight --for record`** prints the same table, then the request count of the newest complete recording (a record folder whose `meta.json` says `recorded`) of the same list, and warns when that count is more than what is left. It only warns; it never blocks.

## Targets

The targets are read from `tools/brain/targets.json` ([format](formats.md#targets-targetsjson)) and judged on KaijuFlow, by `check` and in `report.md` alike. The result of a target is one of:

- **Met** or **Not met**. A time is met when KaijuFlow's figure is no higher than the other side's figure (or the fixed limit) plus the margin. `plays` is met when KaijuFlow's share of played top picks is higher than the other side's share minus the margin, or when both sides played every top pick (spec #58: "at least as often, and more often unless both play every time"; owner, 2026-11-15). So with margin 0 a tie at 40 of 40 is met and a tie at 39 of 40 is not. `plays per round` is met when every cold and warm round played at least the limit minus the margin, and no more counted top picks failed in it than the margin.
- **Inside the noise**, added to Met or Not met for a time target: KaijuFlow's own two rounds of that kind (both cold rounds for a cold target, both warm rounds for a warm one) differ by more than the target is met or missed by. The same run done again could turn such a result around, so do not read it as settled. With a margin, "missed by" is the distance to the other side's figure plus the margin, not to the figure itself.
- **Not measured**: the run holds no figure for it (the side compared with was not in the run, or no top pick played). The measured values then read "no figure".

The targets do not decide whether a run can serve as a baseline: the exit code of `check` is the same with every target missed.
